# Building & flashing the MD-UV390 (10W, AES256) firmware

Based on the official OpenGD77 source release **R20260131** (`OpenGD77_MDUV380_DM1701_20260130`), set up to
build the **MD-UV390 Plus 10W** target (`MDUV380_10W_PLUS_FW` = `PLATFORM_MDUV380` + `PLATFORM_VARIANT_UV380_PLUS_10W`)
from the command line / CI, without STM32CubeIDE.

This release includes the 10W Plus hardware fixes: the screen/backlight and PA control signals are transposed
vs the 5W radios, and newer production batches have low-brightness LCDs - all handled by the 10W_PLUS target.
**Do NOT flash a 5W build to a 10W radio.**

## TL;DR end-to-end (one script)
```sh
# 1. install the official ARM GNU toolchain (14.2.Rel1) and python deps:
pip install -r MDUV380_firmware/tools/requirements.txt
# 2. put the radio in DFU/bootloader mode, then:
./flash.sh /path/to/MD9600-CSV2571V5-V26.45.bin
```
`flash.sh` builds the firmware, validates the codec donor, merges the AMBE codec, and DFU-flashes the radio.

## The AMBE codec donor (required for DMR)
DMR uses the proprietary AMBE+2 vocoder (DVSI-licensed), which OpenGD77 cannot distribute. Neither the source
nor ANY built `.bin` (ours or the official OpenGD77 releases) contains it - the linker reserves an empty region
(`.codec_bin_section_1`, `0x48BB0` bytes at flash `0x0807537C`, auto-generated by `codec_cleaner` at build time
and verified 100% zero). The codec is merged from a **donor** at flash time.

The donor must be **MD-9600 V5**: `MD9600-CSV(2571V5)-V26.45.bin` (official TYT MD-9600 firmware). The MD-9600
shares the STM32F405 CPU and the identical AMBE codec with the MD-UV380/390, so OpenGD77 uses it as the universal
codec source. **MD-UV390 AES firmwares are NOT valid donors** (wrong codec offset). Validate any candidate with:
```sh
python3 MDUV380_firmware/tools/verify_codec_donor.py <donor.bin>     # prints VALID / INVALID
```

## Manual build
```sh
cd MDUV380_firmware
make -j$(nproc)
# -> build/openuv380-10w.bin  (~806 KB: code + reserved codec region)
```
The `Makefile` mirrors the CubeIDE `MDUV380_10W_PLUS_FW` release config (-Os, `-mcpu=cortex-m4 -mfpu=fpv4-sp-d16
-mfloat-abi=hard`, defines `USE_HAL_DRIVER STM32F405xx PLATFORM_MDUV380 PLATFORM_VARIANT_UV380_PLUS_10W NDEBUG
GITVERSION=<git short hash>`, linker
`STM32F405VGTX_FLASH.ld`) and auto-creates the empty codec placeholder via `tools/codec_cleaner.Linux -C`.

## Build flags

Plain `make` is the release build: AES-256 voice is always compiled in and every optional flag is off. A flag is
on only when set to `1` on the make command line (`make ENABLE_FAST_SCAN=1`) or through a named profile
(`make PROFILE=full`). The Makefile refuses combinations that cannot work (`ENABLE_SCAN_PROFILER` without
`ENABLE_SPECTRUM`, both TX pattern diagnostics at once, an unknown profile) and prints a size report after every
link that fails the build when SRAM headroom drops under `RAM_FLOOR` (default 1,024 bytes; `make RAM_FLOOR=0`
to inspect an over-full build). `make profiles` lists the profiles, `make flags PROFILE=x` shows what a profile
turns on, and `make REPRODUCIBLE=1` pins the compiled-in build time to the commit time so two builds of one
commit are byte-identical.

Main SRAM (128 KB) and CCM RAM (64 KB) are the binding constraints, not flash: the release build has 17,452 bytes
of SRAM and 10,104 bytes of CCM spare, and about 111 KB of flash before the fixed AMBE codec slot. Costs below are
measured on this tree with arm-none-eabi-gcc 14.2.1 at -Os (2026-10-24) and are deltas against the release build.

Features that are only live while their screen or command runs share one 11,904-byte SRAM block, the **feature
arena** (`application/source/functions/featureArena.c`): the satellite screen's Keps table owns it while that
screen is on the menu stack (Keps reload on every entry), the VFO sweep's strip, hold and average buffers own it
while the sweep runs, and the USB spectrum probe borrows it for one command. A feature that needs a buffer only
while the user is in it should claim the arena rather than add a static array. Two more moves keep the budget
honest: the notification popup saves only the 80-row band of the framebuffer it can cover (25,600 bytes of CCM
instead of 40,960), and the AMBE codec state (8,448 bytes, encoder and decoder overlaid) lives in CCM, which the
blob addresses through the pointer in r1.

## Manual flash
```sh
cd MDUV380_firmware
python3 tools/opengd77_stm32_firmware_loader.py -s <donor.bin> -f build/openuv380-10w.bin -m MD-UV380
```
The loader patches the AMBE codec into the reserved region, merges language packs, then downloads via DFU.
It prints **"Patching for DMR"** on success (vs **"Flashing FM Only firmware"** if no/invalid donor).

## Build test
```sh
./test_build.sh [optional-donor.bin]   # builds every profile into build-<profile>/, asserts each is codec-merge-capable
```
It also checks that the Makefile refuses the forbidden flag combinations. CI (`.github/workflows/build.yml`)
builds the same profiles with `REPRODUCIBLE=1` and asserts the merge-capable size.

## Host tests (no radio, plain gcc)
```sh
cd MDUV380_firmware && sh tests/run_all.sh
```
Builds and runs every `tests/test_*.c` against the real `crypto/` and `functions/dmr_sms.c` sources with the
small firmware stand-ins in `tests/stubs/` (each test's header carries its own gcc line). Covers the AES
primitives, the late-entry MI and EMB codings, the RX bootstrap / PI seeding across call boundaries, the TX
state at key-up, and the SMS receive path (unconfirmed and confirmed delivery, addressing, retransmissions, the
acknowledgement, the network's short data, and the stock radio's "DMR format" text, from captured PDUs).

## Dual screen build
`ENABLE_DUAL_SCREEN=1` adds the Anytone-style dual screen (two rows, A and B, each a VFO or a zone channel;
Up/Down selects the other row, RED switches the active row between VFO and channel), a row watch that peeks at
the other row every 1.5 s when the active one is quiet, and a "DW Options" menu under Options (dual screen
on/off, row watch, side B = VFO B or the zone channel, home side, speed, stay/switch on a signal). The row
watch looks at an analog other row (a DMR row cannot be judged in a short look); the active row may be analog or
DMR. It tunes to the other row for 80 ms every 1.5 s while the active row is quiet (no audio, and on a DMR row no
call up), shows an "RX" badge on it while a signal lasts, and returns to the active row after the scan hang time,
re-initialising the DMR receiver so a call that started meanwhile is joined by late entry; the active row does
not change. "Home",
"Speed" and "On signal" (stay or switch) belong to the VFO dual-watch scan (the A/B alternating scan),
not to the row watch. Ported from erenbozaci/md-uv390-firmware (Eren TA3BZC), same R20260131 base. State
lives in the two previously unused settings fields, so older settings read as "all off". Verified on the
bench 2026-10-24: menu, rows, row select, VFO/channel switch, persistence across a reflash, row watch with
a carrier on the other row (badge within 2 s, gone 7 s after the carrier).

## TA2TWC screens build
`ENABLE_TA2TWC_SCREENS=1` adds the redesigned screens of josephddt/OpenGD77-TA2TWC (same R20260131 base): a
Channel home screen with large frequency, channel, zone and TX frequency, the S-meter with dBm, signal quality,
noise, battery voltage, temperature and a scrolling signal history; a caller screen with the callsign large;
a TX screen with the time-out bar; telemetry lines on the VFO screen; an analog needle S-meter on the RSSI
screen; boot and shutdown animations with the radio's callsign and DMR ID; a dark default theme and compact
9-line menus. "Main screen: Classic" in the Display options brings the stock Channel screen back. With
`ENABLE_DUAL_SCREEN=1` as well, the dual screen takes the home screen over while its option is on. The fork's
own spectrum module is not taken (this tree's sweep has its waterfall), nor its settings defaults.

## AES
Every build includes DMRA (Motorola/Hytera-compatible) AES-256 encrypted voice — both **transmit and
receive**, interoperable with a stock TYT MD-UV390 ("Universal" AES256). There is no AES-off variant: AES is
the purpose of this fork.

**Checking a build's size.** `arm-none-eabi-size` cannot see code changes in this firmware: `.text` growth is
absorbed byte for byte by the fixed-address AMBE placeholder section (`.codec_bin_section_1`), so its text
total stays 728864 whatever changes. Compare section sizes instead with
`arm-none-eabi-objdump -h build/openuv380-10w.elf` (or `arm-none-eabi-size -A`). Two builds of one commit are
only byte-identical when `SOURCE_DATE_EPOCH` is set in the environment (the build date and time are compiled
into the firmware-info screen) and `GITVERSION=<hash>` is passed to `make` when the trees differ in commit.
Crypto lives in `application/source/crypto/` (host-unit-tested: FIPS-197 AES,
LFSR128d, OFB keystream, Golay(24,12) late-entry MI, EMB BPTC single block); the HR-C6000 and codec hooks are
in `HR-C6000.c` and `dmr_codec/codec_interface.c`.

**Late entry.** A call joined after its PI header (the radio was off, on another channel, or the sender
re-pressed PTT quickly) is bootstrapped from the Late-Entry MI the sender stuffs into the AMBE bits, which
carries the 32-bit MI but no key id. The key comes from, in this order: the key id the sender announces in
the burst-F EMB "Late Entry Single Block" (every DMRA encrypted call carries it; the firmware reads it back
from the HR-C6000 page-0x02 registers 0x29..0x2C on burst F, accepts it only when it decodes cleanly, says
AES-256 and names a loaded slot, and forgets it at the end of the call); then the key the current channel
is configured with; then the key of the previous call; then the lowest loaded slot. A call that started
on a guessed key switches to the announced one as soon as a block decodes, so a lost block costs one
superframe. A PI-seeded call takes its key from the PI and ignores the block. Issue #11 describes the
scenarios: a channel on key 2 joined while the radio sat on a channel keyed with key 1 is decrypted with
key 2 once the block has been read. Whether the chip presents the received block in those registers is
still to be confirmed on a radio (the `dev-aes` build logs the raw word as an `EMBSB` event in
`tools/rxdiag.py`); if it does not, the chain starts at the channel's key as before. Optional, off-by-default diagnostics are gated behind
`DMR_AES_DIAG_RX` / `DMR_AES_DIAG_PATTERN` / `DMR_AES_DIAG_ENCPAT` (e.g. `make DMR_AES_DIAG_RX=1`,
read with `tools/rxdiag.py` / `tools/fragcap.py`). Encrypted voice is for licensed commercial/PMR use only; it
is not legal on amateur bands in most countries.

## USB access for flashing (per platform)

The radio is flashed over USB DFU (STM32 bootloader, VID:PID `1fc9:0094`). USB access differs by host:

- **Linux (native):** install the bundled udev rule so DFU is accessible without root:
  ```sh
  sudo cp MDUV380_firmware/tools/udev/99-gd77.rules /etc/udev/rules.d/
  sudo udevadm control --reload-rules
  ```
- **Windows:** run the loader with Python + libusb, or use the OpenGD77 CPS. The DFU interface needs the
  WinUSB/libusb driver (e.g. via Zadig) bound to `1fc9:0094` while the radio is in bootloader mode.
- **WSL2:** USB is not passed through by default - attach the device with `usbipd-win`
  (`usbipd bind`/`usbipd attach --wsl`) before running `flash.sh`, or just flash from Windows.

Put the radio in DFU/bootloader mode (power on with the side buttons held - see the OpenGD77 install guide)
before running `flash.sh` / the loader.

## Status

**Verified on hardware (MD-UV390 10W Plus):**
- Builds the official R20260131 source for the 10W target; output is structurally identical to the official
  release `OpenMDUV380_10W_PLUS.bin` (codec slot, `.data`/`.ccmram` layout, language tables, size) - the only
  byte differences are toolchain/optimization and an embedded firmware build-date string.
- Codec-merge-capable (806 KB); the AMBE codec from the **MD-9600 V5 donor** merges into the reserved 0xFF slot
  at `0x0807537C` without touching `.data`/`.ccmram`.
- **AES-256 TX and RX interoperate with a stock TYT MD-UV390** ("Universal" AES256): a stock radio decodes this
  firmware's encrypted transmissions to clear voice, and this firmware decrypts a stock radio's encrypted voice
  - including rapid back-to-back calls (the receiver locks the new call's MI from the in-band Late-Entry).
  Cross-checked with HackRF captures + DSD-FME.
- AES key/value storage persists in the SPI-flash custom-data region (survives reboot and firmware flash);
  loaded via the host tool below.

## Loading an AES key (host tool)
With the radio connected over USB (it enumerates as an OpenGD77 CPS serial port, VID:PID `1fc9:0094`):
```sh
pip install -r MDUV380_firmware/tools/requirements.txt
python3 MDUV380_firmware/tools/aes_key_store.py --key <64-hex-chars> --keyid 1 [--tx-key 1] [--port COM4]
```
`aes_key_store.py` writes the key into the OpenGD77 custom-data region (`CODEPLUG_CUSTOM_DATA_TYPE_AES_KEYS`)
using the same CPS flash protocol the CPS uses, so it persists across reboots and firmware flashes. The
firmware reads it lazily on the first encrypted call. `--tx-key N` selects which key id to transmit with
(`0` = encrypted TX off); `--show` dumps the stored block. The on-radio key-entry menu is a planned
alternative.
